## PART 1 — the flag family, scanned from free text

- Fields (db.js): do_not_solicit, do_not_mail, do_not_email, deceased_date,
  address — plus imported_sustainer{,_amount,_last_gift} (Part 5). Semantics:
  do_not_solicit = no ASKS (drift, re-engage, at-risk, suggested outreach,
  ask automations) while stewardship thank-yous and transactional mail
  continue; deceased blocks everything; "do not call" maps to do_not_solicit
  (a fundraiser's call IS an ask).
- detectNoteMarkers (importShape.js, pure): conservative regexes per flag.
  Pinned non-match: "Do not include in vendor mailing" (a note about a
  VENDOR list) flags nothing. "d. Nov 2023" is anchored so "Ph.D." can
  never match. A bequest/estate note sets deceased AND do_not_solicit.
- Every match lands on the import summary under "we flagged these" with the
  matched phrase and line number — a human confirms rather than discovers.
- Pledge cadence (Part 1d): a gift whose note marks it a scheduled pledge
  payment — or that pays a pledges row — inside the trailing 24 months
  excludes the donor from drift as `pledge_cadence` (contractual, not
  voluntary). Detected in SQL inside computeDriftForDonors so pre-BUILD-77
  imports are covered too.
- THE ASK GATE (Part 1f): one predicate (`solicitableSql`) applied to every
  surface with an action button — drift (via exclusions), the day view's
  no-contact/lapsed/matching-gift buckets, computeAtRiskCandidates (the
  AI-drafted re-engagement trigger), computeMilestoneCandidates (deceased +
  DNC; DNS keeps stewardship thank-yous, deliberately), sequence
  auto-enrolls (lapsed_90/180, new_donor), the donor_lapsed workflow sweep,
  and the client Re-engage view + its badge. Thank-you/receipt buckets
  exclude deceased only (a receipt is transactional; DNS stewardship is
  legal and right).

## PART 2 — a bad date became today

- importShape.normalizeDate: full rewrite — the nine formats matched
  EXPLICITLY (m/d/yyyy · m/d/yy · mm-dd-yyyy · yyyy-mm-dd · yyyy/mm/dd ·
  "March 4, 2024" · "14 February 2024" · dd-Mon-yy(yy) · Excel serials,
  epoch 1899-12-30), calendar-validated (2/30 errors), two-digit years
  pivot to the PAST (5/12/99 → 1999), and NO native-Date fallback — the
  native parser is platform-dependent (Chrome vs Node disagreed on
  "03-16-2020"), which is exactly why the browser-only failure was
  invisible to tests.
- EVERY date default removed: the client builder errors the row
  (`unparseable_date`, with its line); the server's normalizeGiftDate
  returns null instead of today twice over, and all four call sites now
  refuse — import paths ledger-error, manual/edit routes 400.
- THE FUTURE POLICY (Part 2c, written down): a gift is a thing that
  happened — a future-dated gift row is an ERROR (`future_date`, line
  numbered). The one legitimate future-money shape is a pledge, which is
  not a gift row (Ruth Caldwell's "Postdated pledge check", 02-11-2027,
  errors with its reason). Manual single-gift entry is not future-gated —
  a human typing a date into a form is a deliberate act on a visible field.
  The golden suite re-derives future-vs-gift per run day, so the fixture
  never rots (three of the key's eight future rows had already become
  valid gifts by the suite's second run day).
- The September 3/September 4 boundary: the fallback stamped
  `new Date().toISOString()` — UTC, i.e. tomorrow every evening — while the
  header showed the org-local day through the BUILD-75 seam. Killing the
  default kills the class; the date audit stays at zero (no new sites).

## PART 3 — the invariant graded its own homework

- ROOT CAUSE: the server ledger's "In your file" counted the PAYLOAD it
  received; the client's builders dropped rows before the payload was
  built. The equation balanced because both sides were computed after the
  losses.
- buildTransactionRows (importShape.js) is THE accounted builder: every
  physical row leaves with exactly one disposition (gift · donor_only ·
  skipped(reason) · errored(reason)); "In your file" is the physical
  non-blank row count taken ONCE at parse entry and carried through; the
  client folds its refused rows into the buckets and recomputes balance
  against the FILE. Fails-first: the pre-fix reproduction read inFile
  2,428/Balanced vs the file's 2,502.
- Formats handled: "USD 750.00" (currency-code prefix — 54 rows,
  $154,849.63 recovered), "(500.00)" and "-$500.00" refunds import as
  NEGATIVE gifts (reduce the dollar total, not the row count — donor net
  lifetime is now true), "$0.00" in-kind/soft-credit rows SKIP with their
  reason (visible, never vanished), blank/" "/"n/a"/"TBD" skip as
  no_amount, and the stray header row echoed into the body errors by name.
- The summary offers a CSV download of exactly the refused rows — line
  number, disposition, reason, and every original column. If an org cannot
  get back what Steward refused, Steward ate it.
- Auto-mapping (Part 3d): autoDetectTxMapping moved into importShape.js
  (the golden suite drives the REAL mapper) and now claims every column
  with a schema home — Phone, Address (new donors.address column), City,
  State, ZIP, Payment Method→type, First/Last/Org name→name composition.
  The fixture's thirteen discarded columns became FOUR genuinely homeless
  ones (Fund — only when a Campaign column exists — Donor Type, Source,
  Legacy ID), which are named on the MAPPING screen and require an
  explicit acknowledgement before the import will run.

## DECISIONS RECORDED ALONG THE WAY

- Pledge installments never count as sustainer interval evidence: twelve
  monthly capital-pledge payments look exactly like a sustainer to interval
  math (the first key draft found 47 "sustainers"; the 13 extras were all
  12-of-12 pledge payers). Pledge marker outranks sustainer inference;
  interval evidence outranks the sustainer note; both recorded in
  detectImportedSustainers.
- $0 rows skip rather than import as $0 gifts: the disposition is visible
  and downloadable; inventing zero-dollar money rows would ripple through
  every money surface for no information gain.
- A latent 500 found while reproducing: an org with a chart of accounts but
  NO fin_funds row 500s /donors/import-combined (parameter-count error in a
  fund-resolution branch). Real orgs get funds at creation; noted, not
  chased in this build.
