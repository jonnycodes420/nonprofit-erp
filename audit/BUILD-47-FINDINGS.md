# BUILD-47 — Find Your Nonprofits + Dashboard Design Pass — FINDINGS

**Date:** 2026-08-12 · **Scope:** donor-side org discovery (directory + add flow + follows) and the /giving design pass. No structural changes; org side byte-untouched.

## What shipped

- **Directory** — `GET /network/directory` (donor session + own rate limiter, 120/15min): searches **listed orgs only** (`portal_settings.enabled AND network_listed` — pending applications ship disabled+unlisted, the delist sweep clears `network_listed`, so all three invisible states fail the predicate *by construction*, not by filter-listing them). Search by name, city/state, or exact-9-digit EIN; LIKE wildcards escaped; results carry only listing-card fields (name, location, logo, colors, the org-editable one-line description — new `portal_settings.directory_description/city/state`, edited in Settings › Donor Portal, visible only while listed). Paginated (20/page), server-side.
- **Add flow** — `POST /account/orgs/add`: ONE code path for all three outcomes. It always (a) upserts a `donor_org_follows` row, (b) clears `unlinked_at` on any link the donor previously hid (an explicit re-add is donor intent — the one sanctioned relink outside `/links/:id/relink`), (c) runs the existing idempotent link job, then returns the same `{ok:true}` body. What the donor sees comes from the dashboard refetch: a verified-email match renders full history (outcome 1); no match renders a **followed** card (outcome 2). The committed suite asserts the two responses are **byte-identical** — no timing/shape oracle for "a record exists under another email".
- **Follows** — dashboard-side state only (`donor_org_follows`, account-scoped, CASCADE on account delete). A followed card shows identity + the org's directory description + a Give path (`/give/:orgSlug`) + the honest connect-your-email copy — **zero history figures**, and the ink summary strip is hidden entirely until the first *linked* org exists (no $0s pretending). Followers see **org-wide impact updates only** (a follow has no gift attribution; fund/campaign-targeted updates never match — asserted). **Conversion (outcome 3)** is automatic: alias-verify already runs the link job; display precedence (link beats follow) completes it. Unfollow deletes the row, audits `unfollowed`, touches nothing org-side. A follow never resurfaces an org the donor explicitly hid (any-link-row exclusion).
- **THE WALL, extended** — no org-side route reads `donor_org_follows` (rule added beside the donor_account* rule in db.js). The §2.4 org-blindness battery now includes the follow scenario in its world-2 exercise (directory searches incl. the other org's exact name, an add-as-follow, conversion on alias verify) and sweeps `dof_`/`donor_org_follows` markers — 48/48.
- **Design pass** — /giving now carries the design language deliberately: full-bleed ink header band (serif cream wordmark, brass rule), ink summary strip with real hierarchy (This-year hero under a brass eyebrow; Lifetime/Organizations secondary behind pine hairlines; stacks at 390), org cards with the org's accent as a left edge + serif names, composed empty state (directory-first, auto-link explanation as secondary copy), styled trust line (hairline + centered). All values from the existing token set; brand-allowlist 27/27.

## Worry paragraph

**Search-surface abuse.** The directory is the network's first *enumerable* surface. What it can leak is deliberately tiny — that a listed org is on Steward, plus the card the org itself typed — but enumeration is still enumeration: an account costs only an email, and 120 searches/15min × patient paging would eventually walk the whole listed set. I judged that acceptable because listing is opt-in precisely to be found, and the gate (EIN check + human approval) bounds who can *be* listed; the thing to defend is that no query shape ever crosses from "which orgs exist" to "who gives where" — the hostile-query battery and the row-key allowlist assert that, and any future directory field must clear the same bar (never add donor counts, "X supporters", or activity signals to a directory row; that's the cheap growth hack that breaks the promise). The add flow is the sharper edge: it's an oracle *by design* for "does org X hold a record under one of MY verified emails" — that's the donor's own data, fine — and the discipline that keeps it from becoming more is that aliases require inbox control before they enter the match set, plus the byte-identical response. The rate limiter on add (30/15min) also bounds follow-spam (an attacker following thousands of orgs costs only their own dashboard noise, since follows are invisible org-side — but it would bloat `donor_org_follows`; acceptable, indexed, CASCADE-cleaned). **At 10k listed orgs** the current alphabetical LIKE search will feel bad before it breaks: "Community" will match hundreds with no relevance order, and city/state fields are free-text (no normalization — "AL" vs "Alabama" both live). Relevance ranking (prefix-weight, exact-name-first, maybe pg_trgm) is deliberately out of scope now; it becomes needed around the point a common word returns more than a page or two (~500–1,000 listed orgs, realistically). The `COUNT(*) OVER()` + OFFSET pagination is also fine at that scale and simple to revisit then. What I'd watch soonest: nothing in the directory row proves the org IS who it says beyond the network gate's approval — two listed orgs with confusingly similar names would both render as equally legitimate cards; the EIN-dispute queue covers the identity claim, but the directory has no visual differentiation for it. If donor-side phishing-by-similar-name ever shows up, the answer is surfacing the EIN on the card (it's already public data), not a trust badge.

## Deliberately out of scope (per brief)

Categories/browse-by-cause, recommendations of any kind (§7 BUILD-46 ban stands), donor-to-org messaging, claiming history without email verification. **Manual support path for history claims (documented, not built):** a donor who cannot receive mail at an old address writes to support; a human verifies identity out-of-band and — only with the org's consent — the org corrects the donor record's email, at which point the normal alias flow works. No code path bypasses inbox proof.
