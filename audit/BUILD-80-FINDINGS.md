## The two rules this build added (enforced, not aspirational)
1. **A refused row is not a neutral event** — donors with refused rows carry
   `has-refused-rows:N`; assessDrift caps them at medium and the sentence says
   why ("One row from the last import could not be read. Nothing we can see
   for over a year.").
2. **A number that is 10% of the file in one row is a parse error until a
   human says otherwise** — the largest-gifts panel on the summary, the
   import-health persistence, and the confirm-before-thank queue item.

## Worry paragraph
The identity resolver is the piece most likely to bite: it now merges more
aggressively than email-else-name ever did, and while every fold is logged
and undoable, an over-merge a user never reviews is still an over-merge. The
guards (no name-joins across distinct IDs or distinct emails, household forms
as candidates, ambiguity never links) all held on two fixtures, but the v3
real-file run is where this earns trust — and that run is blocked on the
file. Second worry: `import-semantics` is a follow-up request; if the browser
closes between the chunked import and that call, pledges/links/health are
silently absent (the import itself is whole). Third: the ~30 genuinely
future-dated filler rows in v2 error as future_date — correct per policy,
but a real file with legitimate post-dated entries (pledge schedules outside
the Pledge Payment type) would need the same routing treatment.
