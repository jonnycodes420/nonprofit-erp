## LIST-2 · The Donors list shows what you asked for (2026-11-04)

The 4 Nov full walk on a demo org (1,008 people) found the list ignoring filters, the Last gift sort reading lifetime, search doing nothing, a blank "Add a photo for undefined" profile, Data health saying "People and their businesses: 184,688", and Review pairs spinning.

- **Filters.** On today's code the stage and owner selects, the tag select and the chips all reach `GET /donors` and the query (driven in a browser on 1,000 made-up people). What was broken: the address held only stage and owner, so a reload or Back dropped the tag, the chips and the sort's direction and showed a wider list under the same controls; the Lifetime filter read the stored `donors.total_giving`, so a donor whose stored total was stale above $20,000 passed "at least $20,000" while the profile said $19,500; a failed list read kept the old count; and while a new filter's answer was on its way the old rows and count stayed on screen unmarked. LIST-1's test stayed green because it called the API only, with stored totals equal to the gifts, and never reloaded the page. Fixed: every filter is in the address; Lifetime (filter and cell) reads `shared/numbers/lifetime.js`; the list says "Updating…" until the answer for the current filters lands; a failed read says so and counts 0.
- **Other lists checked.** Save as group, Groups (dynamic members and the Groups page count), saved views and a Campaign audience built on a Group run the same `buildDonorFilter` and gave the list's people (17 = 17; the stale donor left a Lifetime group). Re-engage reads one server rule (`lapse.reengageSql`) and has no filter bar. Tasks filter on the server by view and scope, their own set. None had the break.
- **Sorts.** Last gift sorted by date already through the header and the select; what was wrong: Name sorted by first name, and Lifetime ascending put the people with no gift first. `donorList.sortSql` now sorts Name by last name then first (an organization by its whole name) and puts no-gift people last either way, with `id` as the tiebreak.
- **Search.** Enter pressed before the answer arrived picked the first row on the list, a "Go to" link (it opened Home). Enter now waits for the answer and opens the top person. A profile opened by id (Cmd+K, a link, Atlas) was drawn from a bare `{id}` until `GET /donors/:id` came back, so it read "Add a photo for undefined" for as long as that read took or forever if it failed; it now shows "Loading this person…", "We couldn't find this person" (a 404) or "Try again". One person rule, `server/donors/personMatch.js`, for the top bar and the list's box: name, email, phone, contact person, household name, a linked organization's name and employer, with case and accents folded by `translate()` (no extension; capitals included because the scratch database's collation is C).
- **Data health.** 184,688 was proposals, not people: every person whose email was at a domain an organization's email also used was proposed with every such organization, and a demo where everyone has an address at one placeholder domain multiplies people by organizations. A domain two organizations share is now nobody's own, and the line counts people plus organizations, each once (1,029-person fixture: 91,106 on main, 12 now). Review pairs answered in 0.02 s on the fixture on main too, so the spinner was not reproduced; `apiFetch` shares one promise across identical GETs in flight, so one read that never settled kept every later "Review pairs" waiting. The panel now reads with its own signal, stops after 20 s with a sentence and Try again, and says "No likely duplicates" at zero.
- **Test.** `tests/list2-list-shows.test.js`, one new suite (the brief asked for these checks). 12 of 30 checks red on main, 30 green after. Planted: stage dropped from the query turned §1 red; Last gift sorted by `total_giving` turned §3 red. Filtered list first rows at 20 ms added latency: 179 ms before, 177 ms after.
