## HARDEN-2 · Fast on a phone, and the loose ends from HARDEN-1 (2026-10-27)

- **Giving pages (item 1).** Every `/give` page loaded the CRM's whole entry (the marketing site, Sentry, the app's shared code: 288 KB of JavaScript compressed) before it could ask for its payload, and drew in 4.5 to 5.1 s on a throttled phone (Moto G Power, DevTools slow 4G). `/give/*` is now served `client/give.html` (`src/giveMain.jsx`: Donate only, Sentry after load), which fetches the page's payload, and on `?memberships` the levels, while the script downloads (`lib/givePrefetch.js`). 108 KB, about 2.2 s, markup unchanged (give3 §5/§7 green). The event page (`/e/<slug>`) is drawn by the API and was already 0.7 s. The local preview gzips, as Vercel does. `tests/perf-giving.spec.js`: LCP < 2.5 s, usable < 3 s, < 200 KB JS, median of three phones; 15 checks red on main.
- **The app's first look (item 2).** On an org of 2,000 people and 10,000 gifts (SCALE-1's seeder, one org), Home on a phone took 12 s: 1 MB of JavaScript compressed, then six boot reads, then Home's two bundles one after the other, all as raw JSON, then a font swap that laid the page out again. Now: every tab but Home is its own chunk; `main.jsx` carries only the marketing paths (`virtual:marketing-paths`, from routes.js at build time) and a prerendered page waits for the site's chunk before React draws, so it never flashes; `app.html` preloads the app's chunks and fonts on an app path with a session; `main.jsx` starts the boot reads, the shell's reads and Home's bundles while the code downloads (`lib/bootReads.js`, `lib/homeReads.js`; prefetched answers are parked once for 30 s, and a write forgets them); every GET is gzipped (never an event stream). Home (with INSIGHTS-1's ladder and cards, `/insights` asked for at boot) on a phone 4.6 s, desktop 0.5 s; Donors 100 rows 26 ms on the server, 0.9 s drawn; a profile 1.2 s. No index was added: the Donors list answered in 26 ms, and every screen met its budget once its payloads were compressed and asked for early. `tests/perf-app.spec.js` holds the budgets.
- **The second import job (item 3).** A commit request that reached the server with no body (the breaker's closed tab releases the held request after its socket is gone, and body-parser skips a finished socket) still made a job: empty sheets, a key of nothing, an insert that collided with nothing, and a plan that refused ("1 question needs an answer first"). 17 of 50 browser runs on main, 50 of 50 over HTTP. Now a commit with no rows is a 400 before any write, finding, retiring and inserting the job happen under one advisory lock per org in one transaction, and the client makes the run id once per preview. fix52 §10: 20 commits at once give one job, one receipt and the file's 124,290.00 to the cent; 3 checks red on main.
- **Restored the old way (item 4).** The one-person and bulk Undo closed only the deletion record they named, so an older open record stayed and the nightly check read a live person as deleted; Clear then Load sample data reused an id with its record still open. One door back, `personTrash.js bringPeopleBack`, closes every open record in the same transaction; an insert that reuses a deleted person's id closes theirs (trigger `steward_person_row_forgets_trash`; closed, never deleted). No other path ever existed in history. Prod is untouched: `scripts/stale-deletions-readonly.sql` counts by org, `scripts/close-stale-deletions.js --org` fixes one org, dry run unless `--apply`. fix54 §5, 4 red before the fix.
- **The nightly check (item 5).** One row per run in `nightly_check_runs` (no org ids, check letters and titles only), written after the read-only checks close. Super-admin Status says Last nightly check: green, which checks went red, or in red that it has not run in 26 hours; `/health.nightlyCheck` carries the same without tenant data, and `npm run status` prints it and exits 1 when stale.
