## REDTEAM-2 · every SQL hit Semgrep found, read and made safe by construction; the database's certificate checked (2026-11-07)

- **The 24 were 39, and none was real.** REDTEAM-1's list came from a scan with `-j 4`. A one-job scan of main found 39 `tainted-sql-string` hits and 1 njsscan `node_sqli_injection`: Semgrep 1.184.0 drops taint findings under parallel jobs (27 of 39 at `-j 8`). Every one was read. No request value reached SQL text. Values were bound, and names came from fixed maps (`RESTORABLE`, the slot map, the removal kinds, a column list) or from Postgres's own catalog. Three are error messages, not SQL. So no test could fail on main for an injection, because there was none.
- **Safe by construction, not by comment.** `server/db/sql.js` is the `sql` tag. SQL text comes only from a template's own literal parts (a frozen strings array, which request data can't make). Every `${value}` is bound. A table or column name goes through `sql.id(name, fixedList)` and a catalog name through `sql.ident`. A request may only choose among texts the code wrote (`sql.pick`). `query`/`run`/`queryTx`/`runTx`/`querySetwise` take a `Sql`. Fixed that way: id lists as one bound array (`= ANY(?::text[])`), intervals as `make_interval(days => ?)` (sequences ×4, trial extension), the trash and set-aside restores, contact and street edits, campaign donor fields, goal tables, pictures, removal undo, the RLS lock and trigger drop. Also the pipeline board and portfolio (`portfolioMembership` now hands back a `Sql`), `/people` and the starter preview. Search keeps each read's text (code only) and its values in two maps. REDTEAM-1's seven `nosemgrep` lines are gone; each is a `Sql` now.
- **What is still open (6), listed with reasons in `scripts/ci/semgrep-sql-open.txt`.** Three billing error messages (not SQL). Three reads that run `groups.js buildDonorFilter` over a rule a person typed or saved: the group page, the volunteer roster, the Donors list. The builder's text comes from the code and every value is bound, but its pieces are strings from ten modules (several shared with the client), so it can't hand back a `Sql` until those move. That is its own build.
- **The SQL gate has no baseline.** `scripts/ci/semgrep-sql-gate.sh` (CI `semgrep` job) runs every JS SQL rule over all app code with one job and `--disable-nosem`. Any finding not on the open list fails, and so does a listed one that has gone. A planted `${req.query.n}` with a `nosemgrep` comment on it turned it red. Taint results also vary by machine: CI on Linux flagged the dispute-won restore in `routes/webhooks.js` (column names from a gift snapshot), which the same Semgrep on macOS did not. It is a `Sql` now. So the gate's answer is CI's, not a laptop's.
- **The certificate.** `server/shared/dbTls.js` gives all three pools their TLS. With `PGSSLROOTCERT_PEM` or `PGSSLROOTCERT_PATH` set, the chain and the host name are checked. pg skips the host check for an IP address, so the IP is passed on. TLS options in the URL are removed so they can't turn the check back off. Unset, it is exactly as before, `/health.dbTls` is `"unverified"` and `npm run status` warns. `tests/db-tls.test.js` builds a throwaway TLS Postgres with a made-up CA. The right CA connects. A decoy CA, a host the certificate doesn't name, and a URL saying `sslmode=no-verify` are refused. `rejectUnauthorized: false` planted back gave four reds; leaving the URL's sslmode in place gave one.
