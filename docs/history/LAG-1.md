## LAG-1 · A confirmed change shows everywhere at once (2026-11-08)

- **Why STALE-2 could not reproduce it.** The 8 Nov fleet measured, on production, confirmed changes that took 30 to 60 seconds to reach the totals. A test boot hides most of that: under TEST_MODE every Insights read waits up to 30 s for the worker's fresh build (`insightsData.insightsFor`). A production read never waits. It serves the stored answer with `stale: true`, and the screen heard about the worker's rebuild only on the bell's 60-second `GET /atlas/activity`. That poll is the 30 to 60 seconds. This build reproduced it on a stack booted the way production is: `NODE_ENV=production`, a web process with `WORKER=off`, a separate `worker.js`, no `SESSION_CACHE_TTL_MS=0`, no `TEST_MODE`, and the built client behind `local-preview.js`.
- **What was not the cause.** Server-side read caches (none hold org figures; `org_summary` is invalidated by the database's own change rows), the service worker (it never touches the API), and Vercel (the API is called cross-origin on Railway, so Vercel's cache never sees it).
- **The rule now:**
  - Every GET answers `Cache-Control: no-store` (`middleware/noStore.js`, mounted beside the audit write). Before this, no GET named any cache policy at all. A route that needs a public cache sets its own header after it.
  - After each write lands, the client follows the worker (`client/src/lib/catchUp.js`). It asks `GET /changes/marks` (`routes/catchUp.js`) a moment after the write, then every half second while the org has after-change events or handlers pending, for 90 seconds at most. It announces each table that moved. The stored Insights have their own mark (`stored_insights` is not in `org_changes`), announced as the new kind `insights`.
  - The deck says "Updating…" in place of its counts while its answer is stale, and re-reads it every 1.5 s until it is fresh. It does the same while the org's first build is "being prepared"; before, that message stayed until a reload.
  - Writes to `/calendar/*` and `/donors/:id/book-visit` are now announced as task, note and person. They used to fall to "other", which re-reads nothing. Deck outcomes (`/insights/outcome|review|link`) are announced as insights.
  - Deleting a gift that has an issued receipt asks "This gift has a receipt. Void the receipt first?" on the page, and Void and delete does both steps. The refusal used to be a browser `alert()`, which an automated browser dismisses. That is why the fleet saw Delete do nothing three times. The 409 now carries `receiptIds`.
- **Not reproduced (OPEN):** see the LAG-1 report for exactly what was tried on W-1108-Finance-06 (the profile's own edit moves the header in about 110 ms) and the per-item table.
- **Test:** `tests/lag1.test.js`, the build's one new suite. Each leg is real clicks against the built client, timed from the moment the write's answer arrives.
