## INSIGHTS-2 · No page waits for a whole-org rebuild, and the load test goes green (2026-11-04)

(LOAD-1's report called this "INSIGHTS-1"; an older INSIGHTS-1 exists.)

**Why.** LOAD-1's load test (10 orgs, 60k people, 20 users) took pages from 6 to 14 s to about 0.2 s typical, but the tail still failed the bar, and the cause was the web's one CPU, not the database: every recorded gift changed the org's Insights fingerprint, and the next profile open (GET /insights/donor/:id, in the above-the-fold bundle) rebuilt the whole org's Insights inside the request, 1 to 1.5 s of blocked event loop on a 25,000-person org, while every other org's request waited. The 10 s guard also found /groups/starters (about twenty whole-org COUNT subqueries in one statement), and retention sat at 7.3 s p95.

**Insights are built on the worker** (`server/insights/store.js`). The job `handler:insights` (key `insights:<org>`) reads the org's rows, runs `insights.computeInsights` (`insightsData.computeFor`) and stores the answer in `stored_insights` (org, day, the fingerprint read before the rows, the body as JSON text). After a change (`afterChange.js`, next to the org summary's refresh) a build is asked for; the queue's one-waiting-row-per-key rule folds a burst of asks into one or two builds, and a build waits at least twice the org's last build time so one busy org never takes more than a third of the worker. A request only reads: the stored answer and the org's fingerprint now. Equal is fresh; different is served with `stale: true` and a build queued; nothing stored yet answers `{ preparing: true, sentence: "Insights are being prepared. They will be here in a moment." }` for that panel only. Each web process fetches and parses a build once (the 25,000-person org's answer is about 26 MB, ~150 ms to parse, once per build). After an Insights button (Done, Not now, Doesn't fit, Review, Link) the answer waits for the worker's build (bounded, `INSIGHTS_BUTTON_WAIT_MS`, 8 s), so the panel she reloads no longer shows what she closed. TEST_MODE reads wait for the queued build too (`INSIGHTS_TEST_WAIT_MS`), so a suite reads what it just wrote; production reads never wait. `stored_insights` is unwatched by the org summary's change triggers (derived from watched rows), is created by its module on first use with RLS on, and keeps three days.

**Starter counts in one pass** (`server/groups/starterCounts.js`). The org's people once, their gifts aggregated once per person, the status computed once (only its two columns the starters read), and each starter a `COUNT(*) FILTER` with the same rule `buildDonorFilter` writes. `groups.memberCounts` is unchanged and still counts saved groups; it is the reference the new suite checks each card against.

**Retention in one read** (`server/reports/retentionFigures.js`). The three years' seven figures each (thirty source reads, one after another) are one statement: each person's gifts aggregated per year window with the sources' own conditions, values assembled as `figure()` makes them. The three years' direct rows run in parallel.

**statusSql's statistics.** The post-import ANALYZE lists now include every table statusSql reads (`donor_rhythm`, `donor_relationships`, `pledges`, `pledge_installments`).
