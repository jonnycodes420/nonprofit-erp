## FIX-50 · A Customer org still acted like a demo (2026-10-26)

- **Why (Justin's Place, prod, 26 Oct).** Kind = Customer, yet the console's Email section said "This is a demonstration organization" for Staff, Donor and Billing mail, and the org's app showed the demo banner. It was created as a demo (`is_demo_org`) and set to Customer before #234, and #234 only cleared the flag when Kind changed. About eight separate rules decided "demo": the flag alone (banner, 2FA, mailbox, QuickBooks, Xero, volunteer reminders, the checklist, the send alarm), the flag plus two seeded ids (onboarding stamp, receipts), the flag plus four ids plus a "(Demo)" name (mail gate and sweeps), and a bare "demo" in the name (the console's guess).
- **One rule: an org is a demo only if its Kind is Demo** (`orgKind.isDemoOrg`, `demoOrgSql` in SQL). Every one of those places calls it. A guess is never Demo. `is_demo_org` stays as a copy of Kind, kept by a trigger (`orgDemoMigration.js`); a seed or provisioning run that creates an org flagged demo, named "(Demo)" or with a seeded demo id gets Kind = Demo when it is created.
- **Migration on boot**: an org with no Kind that the console showed as Demo gets Kind = Demo; then the flag is set to match Kind everywhere, and an org leaving Demo has donor mail off until its switch. Logged as `[fix50]` with counts.
- **The Demo switch** at the top of the super-admin org panel (`POST /admin/orgs/:id/demo`), audit-logged per flip; off puts back the Kind the org had before. The org list shows a small "Demo" label from the same rule.
