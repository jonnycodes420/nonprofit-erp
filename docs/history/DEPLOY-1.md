## DEPLOY-1 · Deploys with no error window, and a queue with nothing stuck in it (2026-11-03)

**Why.** After the JOBS-1 and POLISH-4 deploys the prod AI smoke got HTTP 500 from Ask, and a few minutes later 200, so main went red for healthy deploys. Prod's `/health` showed 9 jobs waiting and 8 running, the oldest waiting about 15 days.

**The stuck queue (found and fixed).** `job_queue_one_waiting` allows one waiting row per key. A running row goes back to waiting when it fails (`finish`) or when its worker dies (`reapStale`). When the same key had been enqueued again while it ran (the debounced `scores:<org>` job is enqueued on every gift), that UPDATE broke the index: `finish` lost its write, so the row stayed `running` with no heartbeat; and `reapStale` was one UPDATE over every stale row, so one such row failed the whole statement on every pass, behind a `.catch(() => {})`. From then on no stale row was given back anywhere, and each held its key's waiting row behind it (`claim` never runs a key that is running). Fixed in `jobQueue.js`: `giveBack` closes a row into its waiting twin; the reaper gives back one row at a time; a run has a lease (one hour, per type with `handle(..., { timeoutMs })`) after which it is a failed try; a waiting row whose type no live worker runs is stopped with "No handler for job X" after a 15-minute deploy grace (`failUnhandled`, reading the job types from `process_heartbeats`); `claim` looks past any number of busy orgs and keys (it gave up after eight); `poke` wakes every idle lane; each claim gets its own lease token in `locked_by`.

**Ask's 500 (not reproduced).** Tried locally: Ask hammered from the first second of a boot; with a stand-in model on and off; with prod's 17 ms round trip; with the web and the worker booting together; with an old process serving while the new one ran the full schema init; without TEST_MODE (the shared rate-limit store live). Every request answered 503 then 200, never 500. The CI logs say: both failing deploys changed db.js (a full schema init on boot) and the two passing ones did not; the failing Ask took 1.3 to 1.5 s against 5.3 s for a good answer, so it failed before or at its first model call; the Agent preview right after it passed. No prod logs were read. The fix covers the window whatever the cause: `/ready` and the request gate wait for every boot step (`bootGate.need`: the database chain with the custom-field step, a warm pool, the shared ESM modules, the AI client, the Ask modules), the old container drains on SIGTERM, and the smoke waits for `/ready` and retries a failed Ask once after 15 s.

**Shutdown.** `server/shared/lifecycle.js`: on SIGTERM `/ready` says 503, the socket closes, requests in flight finish (25 s), a worker claims nothing more and hands back what it still holds (not counted as a try), then exit 0. Railway's draining time defaults to 0, so this needs `RAILWAY_DEPLOYMENT_DRAINING_SECONDS=30` (needs-jonathan).

**The worker in status.** It has no public address, so it writes `process_heartbeats` every 30 s (role, build, job types) and the web's `/health` carries the newest as `worker`. CI's verify step and the smoke wait for both SHAs; `npm run status` prints `queue` (oldest waiting by type and age; yellow over an hour, red over a day) and `worker`.

**The test.** `tests/deploy1-ready.test.js`. Red on main for §2 to §8 (no SIGTERM handling, the reaper, no heartbeat); §1 holds because the gate now covers every need (planted: the gate on the database alone answers Ask 200 during a slow boot step).
