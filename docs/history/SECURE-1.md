## SECURE-1 · Go through Steward the way an attacker would (2026-10-28)

Steward now holds a real customer's donors, so this build read the code the way a hostile reviewer would (16 items: CORS, uploads, headers, rate limits, tokens, tenant isolation, roles, links, input limits, stored URLs and HTML, logging, validation, public endpoints, dependencies, screens that claim success, secrets in history) and fixed ten, worst first, each with a section of `tests/security.test.js` that was run red against main. The worst was an SVG logo: it was stored raw and served inline on www.stewardapp.dev, where the session token sits in localStorage, so a logo could take over any account that opened its link. Now no SVG is stored (the browser draws it as a PNG first) and every stored file is served nosniff with a sandbox CSP. Also closed: donor names merged into email HTML unescaped (the campaign preview ran them); staff could export the whole org and delete gifts and grants others entered; a missing JWT_SECRET fell back to a string in the repo unless NODE_ENV said production (prod's is set, 64 characters, checked without reading it); the no-login cancel link never expired; staff reset tokens were stored in plaintext; any org admin could force the all-org notification retry; invite links, Atlas and import previews had only the general limit; 64 MB bodies were parsed before sign-in; the API sent no security headers and CORS preflights were never cached; a website could be `javascript:`. Closed already and confirmed: the CORS list, webhook signatures, tenant isolation (the matrix walks the live router), portal and invite token strength, no real secret anywhere in git history. Left for SECURE-2: PII in logs and Sentry scrubbing, email and phone validation, whole-table list endpoints, field length caps, a full script CSP for the app, the session token in localStorage (moving to an httpOnly cookie), sign-up enumeration, the partly-sent campaign status, and the xlsx/zod advisories.
