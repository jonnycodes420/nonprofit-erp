## IMPORT-7 · A big single sheet loses no rows, the receipt names its counts, and a big Undo can't hang (2026-11-03)

**Why.** "Import a spreadsheet" kept the first 20,000 rows of each sheet (`readBody`, `MAX_ROWS`) and said nothing: a generated one-sheet 25,000-person CSV landed 19,999 people (the header is a row) under "Imported 19,999 new people." The workbook receipt called the gift rows it sent "rows in the file" (89,681) beside a ledger of every gift row in the gift sheets (92,227). And on 3 Nov a CI shard hung twice at perf-app's Undo of the 25k workbook: one request, no limit.

**Every row.** `readBody` reads every row. A file past `MAX_FILE_ROWS` (200,000 rows, all sheets together) is refused by the preview and the write with a 413 and "This file has N rows. Steward reads up to 200,000 in one file; split it and import each part." before anything is read or written; the screen refuses a file past the 50 MB body itself, with its count. The limit is time, not the body: a 199,000-row sheet reads in 19 s. Lifting the cap showed the reader was quadratic: the near-miss check (`shared/sheetRead.js` `ensure`) compared each new person with every person before it, so 25,000 rows took 67 s to preview. It now asks only the people with the same last name, in the same order: 2.0 s. Peak RSS of the web process for a 25,000-row, 49 MB-body CSV, preview then import: 672 MB (185 MB at boot), locally.

**Each count named.** The commit works out every row's fate per sheet (`sheetAccount`, from the ledger's new `readBySheet`): "12 rows in the People sheet = 12 people created + 0 set aside + 0 errored ✓", the Gifts sheet's "… rows in the Gifts sheet = 8 gift rows written + … set aside + 0 errored ✓", and "… rows in all 2 sheets = …" adding them up (parts that are zero are left out, except set aside and errored). A CSV says "rows in this file". The receipt and Settings, Imports show these lines. The workbook screen's ledger names its sheets and units ("56,177 gift rows in the Gifts 2023-2026 sheet = 55,713 to import + 288 refused + 176 routed"), adds the people sheet's line, and its receipt reads "gift rows sent from the gift sheets = gift rows written + set aside + errored", saying how many of the sheets' gift rows were refused or routed before the write.

**Undo.** An import of more than 5,000 rows (gifts, pledges and the people it made) is undone by the `importUndo` job on the queue; the POST answers 202 and the screen follows `GET /imports/:id/undo-status` with a progress bar. Under that it runs in the request with a 20 s limit (`IMPORT_UNDO_INLINE_MS`); past it, it stops at its next step and hands the rest to the same job. The undo is not one transaction, so before anything is removed it writes to `imports.undo_state` who to recompute and what it has removed so far; a run that picks it up finishes the same undo and counts all of it. perf-app's 25k leg and the new suite wait on the job with their own deadline (`tests/lib/undoWait.js`); a slow undo fails, never hangs. messy-25k (25,034 people, 90,523 gifts) undoes on the queue in the perf leg; a 25,000-person CSV in about 5 s.

**Tests.** `tests/import7.test.js` (one new suite: donor data). Red on main 12 of 14. Planted: `slice(0, 20000)` back in `readBody` turned §1 red (19,999); the 5,000-row hand-off taken out turned §4 red (answered inline). The time-limit hand-off was checked by hand with `IMPORT_UNDO_INLINE_MS=1`: a 3,000-person undo answered 202 in 16 ms and the job finished it.
