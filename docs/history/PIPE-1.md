## PIPE-1 · Merges line up instead of breaking each other, and main fixes itself (2026-11-13)

12 to 13 Nov: GitHub moved `ubuntu-latest` to 26.04 and Chromium crashed on launch, so nothing merged for 14 hours while every tab waited on the fails-twice rule. Once CI-PIN-2404 pinned the runners, `polish4-units` went red on main's own code: that day's "behind last year" gap was exactly -$10,149.50, and the truth check rounded it with `Math.round` (toward +infinity, -$10,149) while Home said $10,150. With 3 to 4 PRs open, keep-current rebased every PR on every merge and restarted its 25-minute CI. And the 3:20 AM staging release ran at 10:24 AM because GitHub ran the scheduled job late.

Choices and why:
- **The merge queue, not more rebasing.** CI runs on `merge_group` with the same jobs and the same required check (`test`). Deploys stay on push to main only. When the queue lands a PR, main's tree is the tree the queue tested, so tree-check trusts that run and main deploys without a second battery. automerge's `gh pr merge --auto` enqueues when main has a `merge_queue` rule (no method flag: the queue's settings choose squash); keep-current does nothing while the rule exists. Without the rule both behave exactly as before, so nothing changes until Jonathan turns the queue on (`docs/needs-jonathan/PIPE-1.md`).
- **The canary is watched from the pinned image.** A job whose image has no runner sits queued, which reads as nothing. `runner-canary.yml`'s `watch` job runs on ubuntu-24.04 beside the canary and turns red if no runner takes it in 20 minutes, or if it fails, is cancelled or is skipped. A scheduled run opens (or comments on) one issue; a run by hand does not unless asked. The browser suite is `screens1-parts`: real Chromium, no server or database, so a red canary is the image and not our stack.
- **One rounding.** `shared/numbers/wholeDollars.js` (half away from zero) is what Home's `money` and the truth check's door check both call. The check's own copy is gone.
- **Fixed dates where the stack allows them.** A pinned stack's clock may not run behind the real one (`tests/clock.js` says why), so "a fixed date" is the next noon in New York on a fixed calendar day (03-02, 06-30, 09-15). The half-dollar fixture puts the gap on exactly -$10,149.50 at whatever date the stack is pinned to.
- **The release listens for CI.** `deploy-staging-release.yml` also runs on `workflow_run` of CI for a push to main. A run inside the window does nothing; a run after a merge that deployed itself finds staging current. The schedule stays as the other trigger, whichever comes first.
- **The fails-twice rule** now says: when main is red for the same reason, fix main in a small `main-fix` PR and keep going; stop only for a setting, a secret or a prod change.

Left open (next build): 30 suites still call `assertSurfacesAgree` on the shard's real clock (listed in `.claude/reports/PIPE-1.md`). Moving each to a stack of its own needs `tests/lib/pinnedStack.js` to boot its server with the shard's full env and mock ports (the Stripe, mail and inbound mocks, the browser dist); without that, about a third of them would fail for reasons that are not the clock.
