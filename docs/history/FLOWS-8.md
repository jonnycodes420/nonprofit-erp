# FLOWS-8 · Things that don't work, or don't say why (first staging night)

Lead 2026-11-12, Tier 2 and 3. Each item reproduced on staging first (https://staging.stewardapp.dev, build a8417a1), by real Playwright clicks: reads in Harborlight, writes in org_stagewalk only. `tests/flows8.test.js` holds one check per item on `tests/lib/flows8Fixture.js`.

- **W-1112-Volunteers-17, Add meeting.** Reproduced read-only in Harborlight: with the person's full name typed and the hit shown but not clicked, Add was disabled, two presses did nothing, and no message showed. The meeting route itself was fine (a stagewalk booking with the hit clicked saved: 201, dialog closed). Add is never a dead button now: a name typed exactly as one hit is that person; anything else says in the dialog what is missing ("Pick who the meeting is with from the names under the search."), and a missing day says so instead of throwing. The in-flight guard is released in a `finally`, so an unexpected throw can't leave it stuck.
- **W-1112-Volunteers-21, Attended → Declined stuck on Saving….** Staging's web logs for 07:14–07:25 UTC: one container (started 05:46, stopped 15:09 for the next deploy), no restart, no crash, no unhandled rejection. Railway's HTTP log for that client: the CORS preflight for `PATCH /events/evt_e567…/attendees/att_cb9d…` at 07:19:21 answered 204 in 2 ms, and **the PATCH itself never reached Railway**. That browser then sent nothing until 07:21:33, while the server answered everyone else. The request did not take the web process down; the browser's connection dropped between the preflight and the write. The bug was ours: the save waited forever. `lib/eventRows.withinWrite` stops waiting after 20 s (the request is not cancelled), says "Steward didn't hear back…", and re-reads, so the row shows what is saved.
- **W-1112-Volunteers-20, Add from Directory.** On staging the picker did find never-given contacts by plain substring, but every word on it said donors ("Search donors…", "No donors to add", "Add 1 donor"), and it was not the Donors list's search (no accents, no household or linked-org match). `/donors/pick?match=person` is `server/donors/personMatch.js`, the Donors list's own rule; the picker says Everyone; Add guest asks first when a person with that exact name is on file (`lib/eventCapacity.newGuestOrOnFile`).
- **W-1112-Fundraising-35, published page "not open yet".** Cause confirmed: the public address answers not-open whenever `orgTakesGifts` is false (no Stripe). The Pages list already said so; the editor, the Overview tile and Publish did not. The editor's read carries `takesGifts` and the sentence (`server/give/takesGifts.js`), with a Connect Stripe link; Publish (editor and card menu) asks first; the tile says "Connect Stripe to take gifts on your pages". The public page is unchanged.
- **W-1112-Fundraising-11X, Top 100 shows 0.** It is TOP100-1's hand-kept list, so it starts empty. The empty page now says that, and "Start from your top donors" (`GET /top100/suggested`, `shared/numbers/topDonors` lifetime, the Top donors order) lists them ticked; one press adds them.
