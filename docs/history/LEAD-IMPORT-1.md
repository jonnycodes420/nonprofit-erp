# LEAD-IMPORT-1 · the QA fleet's morning summary lands on the /ops board

**Why.** Muse now runs a QA fleet: five area agents overnight (Donors, Fundraising, Finance, Volunteers, Atlas and settings) and a lead agent that writes one ranked summary each morning, `lead-YYYY-MM-DD.md`. Each fail has an ID `W-<MMDD>-<Area>-<n>` and a tier (1 money or donor-facing wrong, 2 silent state changes, 3 dead ends, 4 slowness, 5 copy), with repeats ranked above new fails inside a tier. The importer knew only the single-walk shape, and it needed a command line and a commit. Jonathan reads /ops.

**Two shapes, one importer** (`server/admin/leadImport.js`). `readReport(text, fileName)` decides the shape (a file named `lead-…` or text naming tiers, NEW/REPEAT and a fleet ID is a lead summary; anything else is a walk report) and returns one answer either way: the date, what it read, the lines it did not read with why, and an `apply(board)`. A lead line can be a list line or a table row whose header names its columns. The tier comes from the row, else from the heading above it. A fail with no tier, or no NEW/REPEAT, or an area the fleet does not walk is listed as not read, never guessed. A lead fail is applied as a walk FAIL on its check (`Donors-12`), so the existing rules hold: a REPEAT finds the open item, a fixed or verified one is reopened, and a "Passing again" line verifies. The fleet's areas map to Map areas in `ops/map.json`'s `fleet` block (Fundraising opens in Campaigns and journeys, Atlas and settings in Atlas).

**Uploads live in the database** (`ops_imports`, `server/admin/opsImports.js`), append-only, with a unique hash of the text (line ends normalised), so the same file again adds nothing. The board is never stored: it is `ops/board.json` with every upload applied in date order, worked out on each read (`deriveBoard`). The preview runs the same derivation with and without the new file and diffs the two, so what it promises is what the confirm does.

**Closing an uploaded item.** A build still closes items with `scripts/ops/board.js close`. An item that exists only in an upload is not in board.json, so its close is recorded in board.json's `closed` list and applied in the derivation on its date.

**This morning** is the latest upload: its date, counts by tier, its top five in the lead's order with each one's state now, and the items verified on that day or the day before.
