## POOL-1 · A deploy never runs out of database connections, and status says how close it is (2026-11-03)

**Why.** Prod reaches Postgres through Supabase's pooler in session mode, then 15 clients across every process. Each process could open 13 (the main pool's `DB_POOL_MAX` 10, plus the set-wise pool's 3, which never closed). A deploy runs the old web, the new web and the worker at once. On 3 Nov the new web's "pool" boot need (DEPLOY-1: four `SELECT 1` at once) met `EMAXCONNSESSION max clients reached`, rejected once and never tried again, so `/ready` said 503 for 9.5 minutes and Railway failed the deploy; the worker's deploy failed the same way, and `reconcileStripeVsGifts` met it as a job. Jonathan raised the pooler to 40 and set `DB_POOL_MAX=5` on the worker.

**Boot.** `lifecycle.poolReady()` opens one connection and on any error tries again after 1, 2, 4, 8, 10, 10 … s, logging each try once; `/ready` says `pool (retrying: max clients reached)` (`bootGate.retrying`, a word from a fixed list, never the error's text). The database need now starts after it, so a full pooler at boot is waited out instead of `process.exit(1)` from `initSchema`. The four warm connections are gone: the pool opens on use.

**Budget.** The set-wise pool's max is `min(3, max(1, floor(DB_POOL_MAX / 3)))` and its idle connections close after 5 minutes. Every connection carries `application_name=steward-web@<sha7>` or `steward-worker@<sha7>` in the startup `options`, beside `steward.app_connection=on`. A job that meets `EMAXCONNSESSION` or 53300 goes back after a backoff with its try not counted (`jobQueue.finish`), so it is never dead for it.

**Status.** `/health.pool` reads pg's own counters (max, total, idle, waiting, set max and total). The worker's heartbeat carries `{ max, setMax }` (`process_heartbeats.pool`), shown as `/health.worker.pool`. `npm run status` prints `db pool`: 2 × web + worker against `POOLER_SIZE` (default 40), yellow above 80%, red above 100%, with the DB_POOL_MAX to lower. Today: 2 × 13 + 6 = 32 of 40 (80%, ok). The budget is in ARCHITECTURE.md.

**The test.** `tests/deploy1-ready.test.js` §9–§12. §9 boots through a stand-in pooler that answers Supavisor's "max clients reached" for 3 s: red on main (the process exited), green with the fix (connected on the first try after the pooler freed). §10 the set-wise budget, idle close under fake timers, the names. §11 a probe job failing with EMAXCONNSESSION on its fifth try: dead on main, waiting with 4 tries with the fix. §12 the status line at 70/90/110%. Planted: the pool need back to one try turns §9 red.
