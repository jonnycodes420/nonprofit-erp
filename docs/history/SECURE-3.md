## SECURE-3 · Sign-in in a secure cookie, sealed mail, locked database rows, a proven restore, and builders who can't touch prod (2026-11-01)

Jonathan approved the brief on 30 Oct. The lead tab built items 1 and 6; two helper tabs, each with its own worktree and database, built item 2 (`secure-3-mail`) and items 3–5 (`secure-3-ops`).

- **1 · The session also lives in an httpOnly cookie (Release A).** Mid-build, Jonathan changed the rollout to the plan's two releases so nobody is signed out. This build is Release A. Every answer that hands out a staff session sets `steward_session` (`steward_support` for a support session): HttpOnly, Secure, SameSite=Lax, host-only. The answer still carries the token, and the server accepts either (`server/auth/sessionCookie.js`). A write made with the cookie needs `X-Steward-Org` (checked against the session's org by `middleware/orgBound.js`) and the session's CSRF token (`X-Steward-CSRF`, an HMAC of the session id, checked in `requireAuth`). A cookie that stops working is cleared on its 401. The client still sends Bearer, and now sends `credentials: "include"` so the cookie is kept once the API is first-party. `api.stewardapp.dev` went live on Railway during the build, and the CSP now allows it. Release B (the client stops reading `npe_token`) is a later brief: `docs/security/cookie-plan.md` lists what it must do.
- **2 · Synced mail sealed at rest.** A Gmail or Outlook body is sealed with envelope encryption: a data key per row, wrapped by a keyring key, with the key id stored in `interactions.body_key_id`. The attachments the read keeps are sealed too. `note` keeps the one-line summary, and the subject and addresses stay searchable. There is one reader (`server/mail/sealedMail.js` `openInteraction`), and a wrong key fails loudly. Privacy mode screens before sealing, exactly as before. The backfill and key rotation script is `scripts/ops/seal-synced-mail.js`: a dry run by default, for Jonathan to run.
- **3 · The database's own lock.** Nothing in the client talks to Supabase: no key, no supabase-js, CSP clean. On every boot, `server/admin/dbLock.js` turns RLS on for every public table (never FORCE), adds a restrictive deny policy for anon and authenticated, and takes back every grant to anon, authenticated and service_role. `scripts/sql/rls-status.sql` is the read-only check, and `tests/rls-anon.test.js` (the build's one new suite) checks it.
- **4 · A restore that has been proven.** `scripts/ops/restore-drill.js` is a dry run by default. It refuses anything that looks like prod. It was rehearsed on a local copy, and went red on a planted wrong gift.
- **5 · Builders can't reach prod.** `docs/security/builder-access.md` lists what to take away and how. `scripts/ci/builder-access-check.js` runs in `script-guards`: it fails on a prod credential in the build environment, and warns on a machine-level Railway, MCP or Vercel login (`MACHINE_LOGIN_FATAL`, to be flipped once Jonathan logs those out).
- **6 · SECURE-2 leftovers.** `/auth/register` and `/auth/register-org` answer 404 outside TEST_MODE unless a super-admin is signed in. No page used them; sign-up is `/public/signup`. `/donors/ids` answers 500 ids a page, and select-all gathers the pages.
