## JOBS-1 · Background work on a queue, a worker of its own, and reactions that retry (2026-11-02)

**Why.** When a reaction to a gift failed (starting a journey, say), `recordGift` logged it and moved on: the gift saved, the step never happened, nobody knew, nothing retried. Recomputes also started inside requests (the score-recompute crash ARCH-1 fixed came from a timer in the web process).

**The queue was already there.** The brief named pg-boss; ARCHITECTURE.md names `jobQueue.js`, which SCALE-1 built on Postgres and chose over pg-boss. Asked, Jonathan chose to build on `jobQueue.js`. The timed jobs (digests, dunning, campaigns, syncs, the weekly email) were already on it, with retries, a dead state and the Admin console's failed-jobs list. What JOBS-1 adds:

- **The outbox** (`server/shared/outbox.js`, table `events_outbox`). `recordGift` writes the gift and its `gift.recorded` event in one statement (a CTE), so if the gift saves the event saves. It then states the facts its handlers are decided on (gift count after the rollup, the lapsed status at that moment, whether an instalment or a membership was applied), marks the event ready and relays it. `afterChange()` (every other door) writes `donor.changed`. The relay marks an event relayed and inserts its jobs in one statement, so an event moves once however many processes relay; a sweep in every job-running process relays what a door could not, and an event left not ready (its process died) after a minute.
- **Handlers, one file each:** `server/outreach/handlers/` thankYouDraft, sequences, journeys (which then opens the gift's thread, BUILD-81, so a journey's first step still holds the thread); `server/donors/handlers/` afterChange, scores. Each is idempotent (a draft per gift, an enrollment per sequence and person, a journey held to its gift, totals and rhythm recomputed, a crossing once) and throws on an error so the queue retries it; after the fifth try it is `dead`, listed on the Admin console, and counted on `/health` (`queue.stopped`), which `npm run status` prints as `handlers`.
- **`afterChangeNow()`** is the step itself, run by the handler and called directly only by the three doors whose readout needs its answer before it is written (a giving-source read, a QuickBooks read, an import's recent gifts), all background work already. The totals (`recalc`) stay with the write, as recordGift's rollup does.
- **`worker.js`**, and `WORKER=off` on the web as a second way to say `STEWARD_PROCESS=web`.
- **Honest screens:** `outbox.pending()`; the profile's closeness word says "Updating…" while a change of theirs (or the org's scores) is still being recomputed, and the summary re-reads itself.
- **Tests wait for the queue, never for a time:** `tests/lib/drainQueue.js`, called by the helpers' `api()` after every write and by `importWorkSettled`. An import's thank-you count is read from the drafts that exist (`GET /imports/:id/progress`), not tallied as each gift was written.

**The test.** `tests/jobs1-outbox.test.js`: a gift whose journey handler throws (TEST_MODE, a person @jobs1-fail.test) saves, its other handlers run, the journey is tried five times and is listed as stopped; a server killed between the gift and the relay (`JOBS_TEST_CRASH_AFTER_OUTBOX`) leaves the gift and an unready event, and on restart each handler runs once and the totals are healed; every handler run twice leaves the record exactly as it was. Planted: the journeys handler catching its own error (recordGift's old shape) turns §1 red, 4 checks.

**Not done.** The other doors' `donor.changed` event is written after their row, not in its transaction (inside an import's ambient transaction it is). `pledge.installment_due` and `import.finished` were not added: no reaction hangs off them today that is not already a timed job or the after-change step.
