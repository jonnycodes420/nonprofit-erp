## GUARDS-1 · The /health guard checks run in the process that answers /health (2026-10-28)

- **Why.** `npm run status` after the HARDEN-2 deploy read guards FALSE: `reconciliation.notRun` and `webhookSubscriptions.notRun`. Traced from the code, not prod. Both answers live in one process's memory (server.js `reconciliation`, `webhookSubStatus`) and `/health` reads that process. A boot gets 5 minutes' grace (guards.js), and the two checks are due 90 s and 95 s after boot (routes/jobs.js, `perBoot`). FIX-47 moved that slot to each boot but still QUEUED the run, and a queued run goes to whichever process claims it first: the old container while it drains, a worker, or no lane for minutes behind a deploy's backlog (same priority as every other due job). With `STEWARD_PROCESS=web` it never ran at all. Either way /health read `notRun` after the grace, until the next interval (20 min for reconciliation, an hour for the webhook check) happened to land in the right process.
- **Fix.** `perBoot` jobs never touch the queue now: `jobQueue.startLocal` runs each on its own timer in every process, the web included, `firstMs` after boot and every `everyMs` after, skipping a run while one is still going. A run an older deploy left queued still drains once. A deploy resets both answers (they are memory) and they come back about 95 s after boot, inside the grace.
- **Guard.** `tests/scale1-queue.test.js` §8 (an existing suite): a per-boot probe runs in a process with no lanes and leaves no queue row. Against main it was red (ran 0 times, one queue row); green after, 28/28. A real boot with `STEWARD_PROCESS=web` and ticks on: main's code had no reconciliation answer 130 s after boot; the fix had one at 90 s, and the webhook check ran at 95 s (it failed locally only because no Stripe stand-in was listening).
