# FLOWS-16 · Nine meetings that vanished, slow first loads, and Atlas's saves

From lead-2026-11-16. Six items, one PR.

1. **W-1116-Volunteers-16, nine meetings vanished.** Not data loss. Staging's Harborlight holds exactly the meetings its Nov 11 rebuild made, and none of them is on a weekday in Nov 16 to 21. The append-only audit trail since the rebuild shows one meeting cancelled (Area 4's own QA meeting with Alaric Applewhite) and no other meeting write. Two of the nine people the walk named are in no org and no seed. Every write to `calendar_events` is scoped by id, or to meetings whose only people are the person erased. `tests/flows16.test.js` §1 holds that line: a cancel, an event delete, a timeline delete and an erase each leave every other meeting's day, people and place as they were. The 02:25 sighting stays open; it can't be reproduced from any row that existed.
2. **W-1116-Volunteers-35, slow first loads.** Reproduced on staging: `GET /groups` took 4.5 s on every call, not only the first. The Mid-level group (a giving-level rule) took 3 s and the starters 3.4 s, against 60 ms for the same groups on a local copy of the demo. The difference is the set-wise pool: it runs with nested loops off, so these whole-org statements are estimated as very expensive, which crosses Postgres's JIT thresholds. Staging's Postgres can JIT; the scratch Postgres can't (`pg_jit_available()` is false), which is why it never showed locally. The set-wise pool now runs with `jit=off`, the same choice REPORTS-SPEED-2 made for big reads. The page-budget walk now opens Groups and fails a page whose reads take over 3 s (a warning on CI's shared runner). SCALE-4 itself didn't slow the pages: its index and lanes don't touch this path.
3. **W-1116-Atlas-20, a follow-up from a neutral page.** The code read of "follow up with Linwood next Tuesday" leaves the person out, and a giving question keeps its people in `donorIds`, which neither the request's `donor_ids` nor the next request's context read. On Linwood's profile the page filled the gap; on Reports nothing did, so the task had no row to cite and the save said "Saved 0 things." Now the name in the words is read, "him" is the person the conversation was about (before the page's record), a follow-up with nobody asks who, and a save that wrote nothing says "Nothing was saved." (`server/atlas/resume.js`).
4. **W-1116-Atlas-02X, "Which one?" lost the date.** `POST /atlas/:id/answer` rebuilt each step from a fixed list of fields that didn't include `period`, so the clarified question became a lifetime question. Steps now resume whole, minus only what resolving wrote. A question nobody answers for 7 days leaves the bell and is closed by a daily job with a line saying so.
5. **W-1115-Fundraising-32, skipped rows without a reason (repeat).** The rows were distinct people with the raw reason, so a skip from before reasons were kept showed a name only, and one person in two entries showed twice. Now there's one row per skipped step, with a sentence ("Stopped by Dana, Nov 13", "Skipped: no address on file, Nov 12", "Reason not recorded (before Nov 16)") and its entry ("Entered Oct 2 · step 2, Birthday card"). The first fix missed because it added reasons to new skips and left the rows query as it was.
6. **W-1116-Atlas-16 and W-1116-Fundraising-34X.** The branding and receipt previews say they're addressed to a sample donor. `apiFetch` built its error from `message || error`, so a code reached the banner; it now reads the route's sentence first, and a bare code is replaced by a sentence (`client/src/lib/errorCodes.js`). Publishing with nothing changed names the live version.
