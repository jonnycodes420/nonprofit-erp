## LOAD-1 · One slow page can't slow anyone else, and a load test proves ten orgs at once (2026-11-04)

**Why.** On 4 Nov prod jammed twice. In the afternoon a fresh 6,395-person org's Donors list took 146 s; the user refreshed, each refresh left another query running, and /me, /privacy and /home/bundle for every org waited 6 to 23 s behind them for the web's ten connections. Opening one profile fired 46 requests at once. No test had ever run more than one org at a time.

**Request limits** (`server/shared/requestLimits.js`, used by every connection `db.js` and `pools.js` hand out). Each web request runs in an AsyncLocalStorage scope opened by middleware right after the request id. Inside it a connection carries `statement_timeout` 10 s (`REQUEST_STATEMENT_TIMEOUT_MS`), or a named longer limit (`export`, `bulk`: 120 s) for the routes in `LONGER`; the SET is sent only when a connection changes hands between limits, with `pg_backend_pid()` the first time. The wait for a connection stops at the same limit. Both answer 503 with "This took too long; try again or narrow it." (a route that caught the error and answered 500 is turned into 503 by the scope's `res.json`). Counters on `/health.pool.limits`. A GET or HEAD whose socket closes before the answer is abandoned: its held connections' backends get `pg_cancel_backend` from a one-connection side pool, waits are refused, the next statement on a held connection is never started, and a held connection goes back to the pool only after its cancel has landed (so a cancel can never reach the next request's statement on that backend). Writes are not cancelled. Once the answer is sent the scope is done, so work the request did not wait for runs as background, as before. Boot, the worker and the queue's lanes are outside any scope. A bundle's in-process reads (`inProcess.js`) keep the outer request's scope.

**Held across a non-database await.** An audit of every transaction, advisory lock and checkout found no transaction body that waits on anything but the database. The Agent run held an idle client across loopback HTTP calls to the app's own routes (each needing a connection of its own): fixed with `db.onThePool`. Eight advisory-lock holds wait on Stripe or a provider (giving-source, mailbox and calendar sync; auction checkout; recurring pause/resume/cancel, proposal accept, portal actions; supporter auto-renew off). They are money or sync paths whose lock prevents a double charge or double sync; left for a brief of their own (lease rows for the syncs, Stripe with an idempotency key outside the lock for the rest). List with lines in `.claude/reports/LOAD-1.md`.

**ON_TIME_THROUGH.** `lapse.js` looked up `donor_rhythm` and `donor_scores` by `donor_id` alone; both are keyed `(org_id, donor_id)`, so every person read both tables whole. It now names the org (the id's own row's `org_id`; `statusSql` and `impact.js` carry it). The primary key is the matching index, so no DDL. On the 25,000-person fixture: 213 s → 104 ms.

**The load test.** `scripts/load/ten-orgs.js seed` builds 10 orgs (1k, 2k, 5k ×4, 10k ×2, 15k, 25k people; gifts, calls, tasks, journeys, scores, rhythms) with SCALE-1's `seedOrg`; `run` drives 20 users for 5 minutes (Home, Donors, filter, search, profile, log a call, record a gift, Fundraising, a report) and prints p50/p95/max per route. Bar: p95 < 1 s every route, profile open p95 < 1.5 s, nothing over 10 s, no connection wait that gave up, no 5xx. `.github/workflows/load-nightly.yml` runs it nightly on a CI database; `npm run status` shows a `load` line.

**A profile in two requests.** `GET /donors/:id/bundle?p=…` answers any of the profile's reads (`PROFILE_READS`, this person's id only) through `/home/bundle`'s in-process runner, so every figure is the route's own. `client/src/lib/profileReads.js` (`useProfileReads`, in Donors.jsx, which opens the profile) asks before any panel's effect runs for the above-the-fold reads, then the rest once those have answered; each panel's `apiFetch` is handed its answer (`api.js prefetch`, now with `bundle` and `after`). The conversation-suggestions POST writes nothing and no longer throws the parked answers away (`SEEN_ONLY`).

**Tests.** `tests/load1-no-jam.test.js` (the one new suite): two orgs abandon a planted 60 s statement ten times each while /me from a third stays under 200 ms; a caller who waits gets the sentence at the limit. Red on main, green with the fix; planted: timeout 0 turns §2 red, cancel removed turns §1 red. `tests/perf-app.spec.js` gained the profile-open count (≤ 3 before first paint, ≤ 8 in all, never the Donors list again).
